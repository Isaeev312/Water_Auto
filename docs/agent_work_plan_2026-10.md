# План работ для дешёвых агентов: слабые места и промпты (27.10.2026)

Источник пунктов — `review_weak_points_2026-10.md` (§2–§4, входит в PR #63) плюс то, что вскрылось при оформлении этого PR. Задачи §3 рассчитаны на состояние кода после влития PR #63. Здесь каждое слабое место переведено в задачу, которую может выполнить недорогая модель без знания предметной области: с точным списком файлов, критерием готовности и командами проверки.

Принцип разбивки: дешёвому агенту даются **механические** задачи — где решение уже принято, а работа состоит в переносе, переименовании, тесте и правке документа. Всё, что требует **трактовки нормы** или **выбора архитектуры**, в план для агентов не входит и помечено «владелец».

## 0. Как пользоваться

1. Одна задача = один запуск агента = одна ветка + один PR. Задачи в §3 пронумерованы в порядке выполнения; зависимости указаны.
2. Каждому агенту даётся **шапка** из §1 целиком и **промпт задачи** из §3. Больше ничего: агент сам читает `CLAUDE.md`, `README.md` и `docs/ARCHITECTURE.md`.
3. Параллельно можно пускать задачи из разных групп (§2, столбец «Группа»): они не трогают одни и те же файлы.
4. Ревью PR от агента: проверить, что в диффе нет файлов вне списка задачи и нет нормативных чисел в `.cs`. CI (Ubuntu + Windows ru-RU) делает остальное.
5. Если агент написал в отчёте «заблокирован» — это нормальный исход. Не просить его «придумать что-нибудь».

Подходящие модели: Haiku/Sonnet уровня 5.x для задач с пометкой «дёшево», Sonnet/Opus — для «средне». Задачи «владелец» агентам не давать.

## 1. Шапка: общий промпт для любой задачи

Копировать как есть, затем ниже вставить промпт задачи.

```text
Ты работаешь в репозитории Water_Auto — расчёт водяных АУПТ по СП 485.1311500.2020 на C# (.NET 10 SDK, библиотеки net8.0).
Сначала прочитай CLAUDE.md, README.md и docs/ARCHITECTURE.md. Правила из CLAUDE.md обязательны, главные из них:
- Ни одного нормативного числа в C#. Числа норм живут только в data/norms/*.json с указанием документа, пункта и редакции.
- Нормы не трактовать. Если для задачи нужно решить, «как понимать пункт СП», — остановись и напиши это в отчёте.
- Calc ссылается только на Core. Таблица разрешённых ссылок — tests/WaterAuto.Architecture.Tests.
- Физические величины в публичных API — типы-значения (Pressure, Flow, Length, Velocity, KFactor), не double.
- Ошибки расчёта — объекты Issue, не исключения.
- Для формул и этапов Calc: сначала тест, потом код.
- Каждый JSON в data/ объявляет "$schema" и проходит tools/ValidateData.
- Коммиты — Conventional Commits, на русском после двоеточия допустимо. Ветка — одна на задачу, в main не мёржить.

Рабочий цикл:
1. Создай ветку от актуального main с именем из задачи.
2. Сделай ровно то, что описано в задаче. Файлы вне списка «Файлы» не трогай; если без этого не обойтись — остановись и опиши в отчёте, что и почему нужно затронуть.
3. Перед коммитом выполни и приведи вывод:
   dotnet build WaterAuto.sln -c Release        (0 предупреждений, 0 ошибок)
   dotnet test WaterAuto.sln -c Release --no-build
   dotnet run --project tools/ValidateData -c Release --no-build -- data/
4. Закоммить, запушь ветку, открой PR в main по шаблону .github/pull_request_template.md. Если открыть PR нечем (нет gh) — запушь и дай ссылку на compare.
5. Отчёт в конце — строго по форме:
   СДЕЛАНО: список изменений по файлам.
   ПРОВЕРЕНО: вывод трёх команд (числа тестов, предупреждений).
   НЕ СДЕЛАНО / ЗАБЛОКИРОВАНО: что и почему. Если пусто — так и напиши.
   ВОПРОСЫ ВЛАДЕЛЬЦУ: только если без ответа задачу нельзя закрыть.

Чего не делать:
- Не «улучшать попутно»: не переименовывать, не форматировать соседний код, не трогать bin/obj, не менять версии пакетов.
- Не выдумывать значения норм и не брать их из памяти. Источник — только текст СП, если он указан в задаче.
- Не ослаблять проверки, чтобы тесты прошли: если тест падает, причина должна быть названа в отчёте.
- Не использовать git stash; не делать force-push; не мёржить main в ветку без необходимости.
- Если задача оказалась больше описанной — сделать описанную часть, остальное в «НЕ СДЕЛАНО».
```
