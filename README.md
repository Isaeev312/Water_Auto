# Water_Auto

Программа расчёта водяных автоматических установок пожаротушения (АУПТ) по СП 485.1311500.2020. Задача — по минимуму исходных данных выдать всё, после чего в AutoCAD или Revit остаётся только оформить чертёж: раскладку оросителей, гидравлический расчёт, подбор насоса, расчёт РЧВ, расчётную записку, спецификацию и DXF.

> Программа помогает проектировщику, но не заменяет его. Результат перед выпуском проверяет квалифицированный специалист по противопожарным системам.

Связанные документы в `docs/`:
- `ARCHITECTURE.md` — слои, модель, конвейер расчёта, библиотеки, этапы.
- `methodology_sp485.md` — выписка методики СП 485 для программы (таблицы, формулы, ловушки).
- `golden_set.md` — состав «золотого» комплекта ПТ.
- `adr/` — принятые решения.
- `CLAUDE.md` (в корне) — правила для агента, работающего с кодом.

## 4. Конвейер расчёта

```
Исходные данные (DWG/DXF + параметры)
  → 1. Параметры по нормам (группа, i, Q, S, t, шаг; табл. 6.1–6.3)
  → 2. Раскладка оросителей и трассировка
  → 3. Граф сети, начальные диаметры (табл. Б.4)
  → 4. Гидравлика (солвер + нормативный вариант для колец)
  → 5. Диктующая зона; не хватает — DN+ и повтор (Б.1.1.12)
  → 6. Насос: требуемые Q, H (Б.23–Б.30), рабочая точка
  → 7. РЧВ: объём, сравнение с размерами пользователя
  → 8. Проверки: размещение, скорости, уклоны, секции, прил. В
  → Выпуск: записка, спецификация, DXF, JSON, .inp
```

Каждый этап — чистая функция `(модель, нормы, каталог) → (модель, журнал, замечания)`. Журнал (`CalcLog`) хранит каждую величину с пунктом нормы и пометкой «допущение» или «решение пользователя». Из журнала собирается записка.

## 5. Гидравлика и кольцевые сети

### 5.1 Исходные зависимости (СП 485, прил. Б)

Единицы ядра: давление P — МПа, расход Q — л/с, длина L — м, высота Z — м.

| Элемент | Зависимость |
|---|---|
| Ороситель | q = 10·K·√P, K — л/(с·МПа^0,5) |
| Участок трубы | ΔP = Q·\|Q\|·L·(1 + k_м) / (100·Kт), k_м = 0,20 по умолчанию (Б.1.3.13) |
| Геодезика | Z/100 МПа |
| Диктующий ороситель | P₁ = (q / 10K)², q = (1,3…1,5)·i·s, s = 12 м² (Б.1; в тексте 2020 г. опечатка в показателе) |
| Насос | H(Q) — полином по точкам каталога (не меньше 5 точек) |

Запись `Q·|Q|` вместо `Q²` сохраняет знак: в кольце направление потока заранее неизвестно.

Если на вкладке «Местные сопротивления» заданы данные производителя (эквивалентные длины или ξ), они заменяют 20 % на этих участках.

### 5.2 Почему нужен солвер

Для тупиковой сети расчёт приложения Б последовательный: от диктующего оросителя к узлу управления, с выравниванием давлений в узлах (Б.21). Для кольца так не получится: расход делится между ветвями в зависимости от их сопротивлений, и это нужно решать системой уравнений.

СП даёт упрощённый нормативный вариант (Б.1.2.16.1): по 50 % расчётного расхода на каждое полукольцо, а при нормально закрытых разделительных задвижках — 100 % на каждую полуветвь. Water_Auto считает **оба** варианта и в записку и подбор насоса берёт **более тяжёлый** (больший требуемый напор). В записке показаны оба результата.

### 5.3 Метод: глобальный градиент (Todini–Pilati)

Тот же метод, что в EPANET. Сеть — граф: узлы (оросители, тройники, стояки, узел управления, источник) и связи (трубы, насос, эмиттеры).

**Пьезометрическое давление узла:** h = P + Z/100 (МПа).

**Эмиттер как фиктивная связь.** Каждый открытый ороситель — связь «узел → атмосфера» с сопротивлением r_e = 1 / (10K)²: тогда h_узла − Z/100 = r_e·q·|q|, что эквивалентно q = 10K√P. Закрытые оросители (вне диктующей зоны) — просто узлы без связи.

**Неизвестные:** расходы всех связей Q и давления всех узлов с неизвестным давлением h. Известно давление источника h₀ (вход в узел управления или выход насоса).

**Уравнения:**
- для каждой связи: h_i − h_j = r·Q·|Q| (для насоса: h_j − h_i = H(Q)/100);
- для каждого узла: сумма входящих расходов = сумма исходящих.

**Итерация Ньютона** (матрицы инцидентности A12, A10; D = diag(2·r·|Q|)):

```
(A21 · D⁻¹ · A12) · h_new = F(Q, h₀)        ← разреженная симметричная система
Q_new = Q − D⁻¹ · (r·Q·|Q| − A12·h_new − A10·h₀)
```

Система для h решается разреженным Холецким (MathNet.Numerics). Размер — число узлов, на типовой секции сотни, решение мгновенное.

**Детали реализации:**
- начальные расходы: по скорости 1 м/с в каждой трубе;
- малые расходы: при |Q| < 1e-6 л/с градиент берётся по линейной аппроксимации, иначе D вырождается;
- сходимость: max |ΔQ| < 1e-6 л/с и невязка баланса узлов < 1e-6 л/с; лимит 200 итераций; не сошлось — замечание в результате, не исключение;
- после решения: скорость в каждой трубе (≤ 10 м/с напорные, ≤ 2,8 м/с всасывающие, 6.7.1.37), давление на каждом оросителе (рабочий диапазон из паспорта, у СВВ/СВН 0,05–1,00 МПа).

### 5.4 Два режима расчёта

**Проектный (требуемое давление).** Нужно найти, какое давление обеспечить на входе, чтобы диктующий ороситель получил P₁. Давление источника h₀ — неизвестное. Внешний цикл (метод секущих): задать h₀, решить сеть, сравнить давление диктующего оросителя с P₁, поправить h₀. Сходится за 3–6 шагов, потому что зависимость монотонна. Результат: Q_с (сумма расходов оросителей зоны) и P_тр на входе → P_н по Б.30.

**Проверочный (рабочая точка насоса).** Насос — связь с характеристикой H(Q), источник — уровень воды в РЧВ. Солвер находит рабочую точку. Проверка: давление диктующего оросителя ≥ P₁, расход ≥ нормативного. Это объясняет случаи вроде эталона ИОС2.2, где подача по проекту (184,80 м³/ч) больше расчётной (168,84 м³/ч): это точка на кривой насоса.

### 5.5 Диктующая зона

Диктующая зона — площадь S по нормам (для группы 2 — 120 м²), при работе которой требуется наибольшее давление на входе.

1. Кандидаты: прямоугольные зоны площадью ≥ S из целого числа оросителей, сдвигаемые по сетке с шагом одного оросителя по всем секциям.
2. Для каждого кандидата открыты только оросители зоны; проектный режим (5.4) даёт P_тр.
3. Диктующая зона — максимальный P_тр, при равенстве — больший Q_с.
4. В журнал пишутся три лучших кандидата и причина выбора.
5. Отсечение: сначала грубая оценка по самым удалённым зонам, полный расчёт — только для 20 лучших.

Форма зоны (соотношение сторон, ориентация вдоль рядков) — открытый вопрос, согласуется со специалистом; задаётся параметром.

### 5.6 Контроль корректности

- **Тупиковая сеть:** солвер обязан совпасть с последовательным расчётом приложения Б (Б.9–Б.22) до 1e-4 МПа. Это отдельный тест, он же проверяет солвер на кольцах «по частям».
- **Эталон ИОС2.2:** q, ΔP по участкам, Q_с — с точностью округления проекта.
- **EPANET:** экспорт `.inp` (эмиттеры с показателем 0,5) и сравнение. Формулы потерь в EPANET другие, поэтому допуск, а не совпадение до знака.
- **Свойства:** баланс расходов в каждом узле, сумма потерь по любому замкнутому контуру = 0, при удвоении K давление на оросителе падает.

### 5.7 Проверки топологии перед расчётом

Ошибка (расчёт не запускается): граф несвязный; нет источника; труба нулевой длины; ороситель не подключён.
Замечание (расчёт идёт): уменьшение DN по направлению потока к источнику; тупиковый подводящий трубопровод при четырёх и более узлах управления (6.7.1.43); на кольцевом ремонтном участке больше трёх узлов управления (6.7.1.42).

## 6. Форматы данных (JSON)

Все форматы — JSON (UTF-8), каждый описан JSON Schema (draft 2020-12) в `data/schemas/`. Сериализация — `System.Text.Json` с source generators. Проверка при загрузке — JsonSchema.Net. В каждом файле есть `schemaVersion`; при изменении формата пишется миграция.

Числа хранятся в единицах ядра (МПа, л/с, м, мм для геометрии), единицы указываются в поле `units` или в схеме. Десятичный разделитель — точка (JSON).

### 6.1 Нормы — `data/norms/sp485/*.json`

```json
{
  "$schema": "../../schemas/norms.schema.json",
  "schemaVersion": 1,
  "doc": "СП 485.1311500.2020",
  "edition": "с изм. № 1 (введено с 01.01.2026) и № 2 (введено с 09.07.2026)",
  "clause": "табл. 6.1",
  "source": "откуда перенесено и как сверено",
  "verified": false,
  "records": [
    {
      "id": "sp485.t6_1.group4_2",
      "clause": "табл. 6.1",
      "values": { "i_water": null, "i_foam": 0.17, "Q_water": null, "Q_foam": 65, "S": 180, "t_min": 60, "maxSpacing": 3 },
      "units": { "i_water": "л/(с·м²)", "i_foam": "л/(с·м²)", "Q_water": "л/с", "Q_foam": "л/с", "S": "м²", "t_min": "мин", "maxSpacing": "м" },
      "attrs": { "group": "4.2" },
      "note": "i_water, Q_water: в таблице «-»."
    }
  ]
}
```

Правила: одна запись — одно значение или одна строка таблицы; `id` неизменен; в коде нет ни одного нормативного числа. В `values` только числа и `null`; `null` — значения в ячейке нет, причина в `note` или ссылка в `refs` (`"refs": { "i_water": "табл. 6.2" }`). Нечисловые признаки строки (стандарт трубы, группа) — в `attrs`. У каждого ключа `values` есть единица в `units`. `verified: false` — значения перенесены, но не сверены специалистом с официальным текстом. Схема — `data/schemas/norms.schema.json`; то, что схема выразить не может (единицы, `null`, уникальность `id` во всех файлах), проверяет `tools/ValidateData`.


```json
      "id": "lowara.nscs100-315-300",
```

```json
{
  "schemaVersion": 1,
  "name": "Паркинг №2, Маликова 91",
  "normsSnapshot": { "doc": "СП 485.1311500.2020", "edition": "…", "hash": "sha256:…" },
  "settings": { "localLossFactor": 0.20, "tankMode": "aupOnly", "zoneAspect": 1.5 },
  "floors": [ { "id": "F-1", "level": -3.3, "rooms": [ "…" ], "obstacles": [ "…" ] } ],
  "network": {
    "nodes": [ { "id": "N-0001", "type": "sprinkler", "x": 12500, "y": 4300, "z": -0.15, "sprinkler": "tyco.ty365.57" } ],
    "pipes": [ { "id": "P-0001", "from": "N-0001", "to": "N-0002", "dn": 25, "standard": "ГОСТ 3262", "length": 3.2 } ]

```

## 7. Импорт DWG/DXF

Проектировщик чертит по шаблону `data/templates/WaterAuto_layers.dwg` (единицы — мм) и загружает DWG или DXF. Чтение — ACadSharp.

| Слой | Объект | Что читается |
|---|---|---|
| `ПТ_КОНТУР` | замкнутая полилиния | контур помещения; имя — текст внутри |
| `ПТ_КОЛОННЫ` | замкнутая полилиния или блок | сечение колонны |
| `ПТ_БАЛКИ` | замкнутая полилиния | **Толщина = высота балки, мм**; Уровень = отметка низа перекрытия |
| `ПТ_КОРОБА` | замкнутая полилиния | Уровень = отметка низа короба |
| `ПТ_ЗАПРЕТ` | замкнутая полилиния | зона без оросителей |
| `ПТ_ВВОД` | точка или блок | стояк, узел управления |

Ошибки импорта (с координатами): незамкнутый контур, объект вне контура, балка с толщиной 0, пересечение контуров, нет `ПТ_ВВОД`.

Выход — DXF в тех же координатах: `ПТ_ОРОСИТЕЛИ`, `ПТ_ТРУБЫ`, `ПТ_УЧАСТКИ`, `ПТ_ДИКТ_ЗОНА`, `ПТ_ЗАМЕЧАНИЯ`. Файл накладывается поверх чертежа пользователя.

## 8. Соглашения по коду (C#)

- Ядро и библиотеки: `net8.0` (совместимость с AutoCAD 2025+ и Revit 2025+). Приложение: `net8.0-windows`, WPF.
- `Nullable` включён везде, `TreatWarningsAsErrors` в Core и Calc.
- Единицы — типы-значения `Pressure`, `Flow`, `Length`; в публичных API нет голых `double` для физических величин.
- Имена: английские в коде, русские — в данных норм, сообщениях и отчётах. Ресурсы сообщений — в `.resx`.
- Ошибки расчёта и нарушения норм — объекты `Issue` (код, уровень, узел/труба, пункт нормы, текст), не исключения. Исключения — только для ошибок программы.
- Без статического состояния и `DateTime.Now` в ядре; время и пути передаются извне.
- Сначала тест, потом код для формул и этапов Calc.

`Directory.Packages.props` — централизованные версии пакетов (`ManagePackageVersionsCentrally`). `global.json` фиксирует SDK с `rollForward: latestFeature`.

## 9. Работа с GitHub

### 9.1 Репозиторий
- Приватный репозиторий `WaterAuto`, ветка `main` защищена: только через PR, обязательный зелёный CI, запрет force-push.
- `.gitattributes`: `* text=auto eol=lf`; `*.cs`, `*.json`, `*.md` — текст; `*.dwg`, `*.dxf`, `*.pdf`, `*.docx`, `*.xlsx` — `binary`. Большие эталонные DWG/PDF — через Git LFS.
- `.gitignore`: стандартный для .NET (`dotnet new gitignore`) плюс `out/`.
- Проектная документация заказчиков (чертежи объектов) в репозиторий не кладётся, только обезличенные эталоны.

### 9.2 Ветки и коммиты
- Ветки: `feat/<кратко>`, `fix/<кратко>`, `norms/<кратко>`, `docs/<кратко>`.
- Коммиты — Conventional Commits на русском или английском: `feat(calc): солвер колец GGA`, `fix(import): балка без толщины`, `norms(sp485): табл. 6.2`.
- Одна задача — один небольшой PR. Крупное решение (солвер, формат файла, библиотека) — ADR в `docs/adr/NNNN-название.md`.

### 9.3 Задачи (Issues)
Шаблоны в `.github/ISSUE_TEMPLATE/`:
- **Ошибка расчёта** — объект, ожидалось, получено, источник ожидаемого значения.
- **Вопрос по норме** — пункт, варианты трактовки, кто решает. Агент не трактует норму сам, а создаёт такую задачу.
- **Задача разработки** — что сделать, критерий готовности, тесты.

Метки: `calc`, `hydraulics`, `import`, `reports`, `norms`, `catalog`, `ui`, `golden`, `question`.
Milestones соответствуют этапам из `ARCHITECTURE.md` (0…7).

### 9.4 Pull Request
Шаблон `.github/pull_request_template.md`:
- что изменено и зачем, ссылка на задачу;
- затронуты ли нормы или формулы (если да — пункт СП и тест);
- прошёл ли эталон `Golden/IOS2.2`;
- новые зависимости (лицензия).

### 9.5 CI — `.github/workflows/ci.yml`

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]

jobs:
  core:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { lfs: true }
      - uses: actions/setup-dotnet@v4
        with: { global-json-file: global.json }
      - run: dotnet restore WaterAuto.Core.slnf
      - run: dotnet build WaterAuto.Core.slnf -c Release --no-restore
      - run: dotnet test WaterAuto.Core.slnf -c Release --no-build --logger trx
      - name: validate json
        run: dotnet run --project tools/ValidateData -- data/

  app:
    runs-on: windows-latest
    needs: core
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { global-json-file: global.json }
      - run: dotnet build WaterAuto.sln -c Release
```

`WaterAuto.Core.slnf` — фильтр решения без WPF, чтобы ядро и тесты собирались на Linux быстрее. Отдельный шаг проверяет все JSON в `data/` по схемам.

### 9.6 Релизы — `.github/workflows/release.yml`
- По тегу `vX.Y.Z`: `dotnet publish src/WaterAuto.App -c Release -r win-x64 --self-contained -p:PublishSingleFile=true`, архив прикрепляется к GitHub Release.
- В релиз входят версия норм (`edition`) и список изменений.
- Версия — SemVer: мажорная меняется при несовместимом формате `.waproj`.

### 9.7 Dependabot
`.github/dependabot.yml`: NuGet и GitHub Actions раз в неделю. Обновления пакетов идут обычным PR через CI.

### 9.8 Работа с агентом (Claude Code)
- Агент читает `CLAUDE.md` и `docs/ARCHITECTURE.md` перед работой.
- Агенту даётся одна задача из Issues, он работает в отдельной ветке и открывает PR.
- Агент не мёржит в `main`; проверяет и мёржит человек.
- Если в данных норм нет нужного значения или пункт допускает разные трактовки — агент останавливается и создаёт задачу с меткой `question`.

## 12. Открытые вопросы

- Форма и правила перемещения диктующей зоны.
- Нужен ли сертификат программы для экспертизы в КР.

- 20 % местных потерь: Б.1.3.13 (все трубы, включая УУ) и пояснение к Б.30 (подводящий и питающий) расходятся; ГидРаВПТ берёт 20 % дважды (В-02).
- Множитель 1/0,95² (= 1,108) на всех трубах, кроме ПК, в ГидРаВПТ 2.9.6 — выяснить (В-05).
- Формула Б.1: в тексте с Изм. № 1 (база ФГБУ «РСТ») — p₁ = (q/10K)²; официальную публикацию сверить (В-08).
- Эталон ИОС2.2 как условие мёржа: в проекте расхождения (В-10).
- Наружное пожаротушение в режиме РЧВ «с ВПВ»: автоматически или вручную (сейчас вручную).
